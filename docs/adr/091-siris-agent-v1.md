# ADR 091 — SirisAI Agent v1 (Tool-Using, Training + Health)

## Status

Accepted.

## Context

Brad asked to keep developing SirisAI/Ollama integration, specifically wanting "an AI agent you can ask anything using Ollama as the backend." Every existing Ollama-touching feature in SirisOS -- SirisHydro's evidence synthesis (ADR 057), Ask Siris's answer rephrasing (ADR 071), "Can I Train Today?" (ADR 081), Coach's weekly headline (ADR 090) -- follows the same rule without exception: a deterministic service computes the facts first, and Ollama's only job is to phrase them more naturally, with a fail-open contract when Ollama is unavailable. "Ask anything" is a genuinely different shape of feature, and it was worth confirming the architecture explicitly rather than assuming, given how load-bearing that no-fabrication rule has been across this entire session (it's what shelved Training Level's Recovery dimension, kept muscle-group tagging athlete-assigned, and kept Strength Score strictly self-relative).

Confirmed with Brad before building: this must still be grounded, not free-form chat against Ollama's own training data. The shape chosen is tool-calling/function-calling -- Ollama gets a fixed set of tools backed by real SirisOS services, decides which to call based on the free-text question, and composes its final answer only from what those tools actually return. This is also the concrete first step toward the architecture direction already discussed and recorded (not yet built, predating this ADR): "treat SirisHydro as an agent within SirisOS, so it can build a memory" -- this ships the tool-using-agent half of that shape, scoped to Training + Health rather than SirisHydro's document corpus, since this session already has deep, well-tested deterministic services in that domain to wire up as tools with no new data-access code.

Scope confirmed as Training + Health only for v1 (not Homelab/Knowledge/Projects) -- a substantially smaller first build, reusing exactly the services this session already shipped and tested (Strength Score, Training Level, muscle-group fatigue, weekly training load, Health summary, training conflict, achievements, recent runs/workouts).

## Decision

**`OllamaChatClient.chat()`** (new, alongside the existing single-turn `complete()`) supports multi-turn messages and an optional `tools` parameter matching Ollama's `/api/chat` function-calling contract, returning an `OllamaChatResult` with either `content` (a final answer) or `tool_calls` (what to call next). Same fail-open contract as `complete()`: disabled configuration, network errors, and malformed responses all return `None`.

**`SirisAgentService.ask(messages)`** runs the orchestration loop: build the conversation (a system prompt plus the caller's message history), call Ollama with the tool definitions, and if Ollama requests tool calls, dispatch each to the real backing service, feed the (JSON-serialized, always-real) results back as `tool` messages, and loop -- capped at `MAX_TOOL_ITERATIONS = 5` so a model that never settles can't loop forever. The system prompt is explicit: "always call a tool before stating any specific number, date, or fact... never invent or guess... if none of your tools can answer a question, say so honestly." Nine tools are registered, one per already-shipped deterministic capability: `get_strength_score`, `get_training_level`, `get_muscle_group_fatigue`, `get_weekly_training_load`, `get_recent_runs`, `get_recent_workouts`, `get_health_summary`, `get_training_conflict_today`, `get_achievements`. A tool dispatch failure (unknown name, or the underlying service raising) is caught and fed back as an error result rather than crashing the turn -- the agent can acknowledge it couldn't fetch something instead of the whole request failing.

Conversation state is **client-side, not server-side**: the Flutter client resends the full turn history on every request, and the backend is stateless per call. Automatic conversation capture into Siris Memory (ADR 061) is explicitly not built here -- it's a named, still-undecided question in the architecture-direction notes ("what memory means here" was never scoped), and bolting an assumption onto it now would be exactly the kind of decision this app has consistently preferred to confirm rather than guess at.

**Where this got registered surfaced a real, pre-existing piece of confusing wiring**: production actually runs `uvicorn app.entrypoint:app` (`deploy/supervisord.conf`), not `app.main:app`. `main.py` owns the legacy core routes plus a few routers pulled in transitively through `running.py`'s own internal `include_router` cascade (gym/health/coach/training among them); `entrypoint.py` is the newer, explicit registry for "everything else" (siris_memory, projects, knowledge, etc.), per its own docstring. This session had been running `uvicorn app.main:app` for every local verification all along, which happened to work because every feature built so far routed through the `running.py` cascade -- but a router registered only in `entrypoint.py` would 404 under that command. The new `/api/v1/siris/agent/ask` endpoint is registered in `entrypoint.py`, matching `siris_memory`'s precedent and the file's own stated intent; live verification for this slice used `uvicorn app.entrypoint:app` specifically, and confirmed `/coach/weekly-report` and `/siris/memory` still work unchanged under it.

Flutter: the "Siris" module (`More → Siris`) is now a two-tab hub (`SirisHubScreen`, mirroring `EngineeringHubScreen`'s existing `TabBar` pattern) -- "Chat" (new) and "Memory" (existing, untouched). The chat screen is a genuine multi-turn conversation UI (scrolling message bubbles, text input), not a single-shot Q&A box like Ask Siris/SirisHydro -- matching "agent" rather than "answer engine." An `OllamaStatus` chip (reusing the existing shared service from Intelligence, ADR 058) shows connectivity at a glance, and each assistant bubble that used a tool shows a small "Checked: strength score, recent runs" caption for the same transparency SirisHydro's citations already establish as this app's convention.

## Consequences

- No new fabrication surface: every fact the agent can state is traceable to one of the nine tool calls, each a direct pass-through of an already-shipped, already-tested deterministic service -- no new data-access or aggregation logic was written for this slice.
- This dev environment has no Ollama server available (`ollama` isn't installed locally), so the actual tool-selection behavior of a real model was never exercised -- only the orchestration loop itself, against a scripted fake `chat_client` covering: direct answer, single tool call, multiple tool calls in one round, an unknown tool name, a real dispatch returning real data (verified against actual seeded `GymService` state, not just shape), Ollama going unreachable mid-loop, and the iteration cap. The `chat()` method's real Ollama JSON-parsing (tool_calls extraction) is separately covered against a stubbed HTTP response, but never against a live server's actual response shape. This is a real verification gap, stated plainly rather than implied away.
- Backend: 258 tests pass (14 new: 5 for `OllamaChatClient.chat()`, 9 for `SirisAgentService`). Flutter: 58 tests pass, unchanged -- the new UI is composition-heavy with no new pure-logic helper worth extracting (the loop/dispatch logic that matters is entirely backend-side and already tested there).
- Live-verified end-to-end in the browser via the fail-open path (no Ollama configured): the Chat tab sends a message, shows it immediately, and receives the correct "Ollama needs configuring" reply with the right status chip -- confirming the full request/response/render pipeline works, independent of the untested real-model tool-selection behavior above.
- Homelab/Knowledge/Projects tool access remains explicitly out of scope, along with automatic Memory capture from conversations -- both are named, deferred, not silently dropped.
