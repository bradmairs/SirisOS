# ADR 095 — Apple Health Integration Overhaul: Timezone Fixes, HRV, Readiness Score

## Status

Accepted.

## Context

Brad reported three concrete problems with the live Apple Health integration and asked for it to be strengthened generally: daily step counts didn't match Apple Health's own app (suspected timezone/day-boundary bug); sleep data from the night before often wasn't showing; and metric units displayed with raw underscored enum names (e.g. "63 Beats_per_minute"). He also asked for heart rate variability (HRV) to start being imported, for more health data generally, for SirisAI to be able to answer health questions (it already could -- `get_health_summary`, ADR 091 -- but this wasn't obviously visible to him), and for a new daily readiness/recovery score driven by sleep and HRV, tracked over time and graphed.

## Decision

**Timezone default and wiring.** `HEALTH_TIMEZONE_NAME` defaulted to `"Australia/Sydney"` -- functionally identical to Melbourne (same AEST/AEDT rules) so not itself a bug, but `SIRISOS_TIMEZONE` was never actually passed through `docker-compose.yml`'s environment block despite the code reading it, so the override was silently inert in production. Both fixed: default changed to `Australia/Melbourne`, and the env var wired through `docker-compose.yml` and documented in `.env.example`.

**Step day-boundary bucketing was already correct** (`HealthIngestService._bucket_day`, covered by `test_health_daily_totals.py`) -- verified by direct code audit and a fresh regression test rather than assumed. If steps still don't match Apple Health after this ships, the next thing to check is whether the production server has actually been redeployed since ADR 088's earlier timestamp-parsing fix, not this bucketing logic.

**Sleep bucketing was genuinely broken**, and is now fixed. A real night's sleep straddles midnight; bucketing every sample by its own plain local calendar day split one night's data across two days, so "last night's sleep" looked mostly missing. Sleep now buckets to the day the athlete woke, using a shifted-clock trick (`_bucket_day`): any sample between `SLEEP_DAY_CUTOFF_HOUR` on day D and the same hour on D+1 lands on D+1. The cutoff itself needed a second iteration during live testing: an initial noon cutoff correctly grouped real sleep segments, but also governed how "now" buckets when computing today's live total -- with a noon cutoff, checking the app in the evening (before that night's sleep had even started) showed a false "0" instead of the completed prior night. Moved the cutoff to 20:00, safely between any realistic wake time and bedtime, so last night's total stays visible through the whole day rather than resetting hours early.

**A second, previously-undiscovered timezone bug was found live while testing the readiness score**, in `TrainingConflictService`, not `HealthIngestService`: `_for_reference_day` compared a health sample's raw UTC `.date()` against `reference_date` instead of converting to local time first, so genuinely same-day HRV/resting-HR data read as "not synced for today" for roughly half of every day (whenever the UTC and Melbourne calendar dates differ, i.e. every evening). `check()`'s own default `reference_date = date.today()` had the same class of bug one level up -- `date.today()` uses the server process's system timezone, typically UTC in a Docker container, not Melbourne. Both fixed by exporting a public `HealthIngestService.to_local_date()` and using it in both places. Neither bug was caught by the existing test suite because every existing test's synthetic timestamps happened to fall in the "safe" morning-UTC window where UTC and local dates agree -- a new regression test uses a timestamp specifically in the danger zone.

**Unit and metric-name display.** Raw values reaching the UI were whatever the ingestion source used verbatim -- HealthKit's own `SCREAMING_SNAKE_CASE` enum names (`BEATS_PER_MINUTE`, `MILLISECOND`) -- never formatted for display. Centralised two functions in `health_snapshot.dart` (`healthMetricDisplayName`, `healthMetricFriendlyUnit`) used everywhere a metric type or unit reaches the UI: the "Today" tiles, the Recovery baseline rows, the metric history screen, and the Sync card's "Metrics tracked" list. Known units map to short forms (`bpm`, `ms`, `kg`, `%`, `min`); `count` (steps' own unit) maps to nothing, since "7,500" reads better than "7500 count". Unmapped units still get underscores replaced with spaces rather than showing raw.

**HRV and more health data.** `HealthKitSyncService._metricTypes` never included `HEART_RATE_VARIABILITY_SDNN` -- `TrainingConflictService` had recognised the metric type name `heart_rate_variability` since it shipped, but nothing had ever synced data for it. Added, plus blood oxygen, respiratory rate, body fat percentage, and flights climbed -- a deliberately modest expansion (VO2 max still isn't exposed by the `health` plugin) rather than syncing every available HealthKit type.

**Daily readiness/recovery score** (`ReadinessService`, new). Self-relative like every other score in this app (Strength Score, Training Level, `HealthMetricSummary.baseline_ratio`): each of HRV and sleep duration is expressed as a percent of the athlete's own trailing 14-day baseline, and the score is the average of whichever of the two have enough history for that day, clamped to [0, 100]. A completely typical day (both metrics at their own baseline) scores 100, not a ceiling reserved for unusually good days; below-baseline HRV or sleep pulls it down proportionally. Neither metric alone determines the score if the other is available; a day with neither metric's history gets no score rather than a fabricated one. Built entirely from `HealthIngestService.daily_history()` -- no new table, matching how every other derived score in this app is computed live rather than cached.

**SirisAgent** gained a 13th tool, `get_readiness_score`, wrapping `ReadinessService.today()`. `get_health_summary` (ADR 091) already let Siris answer general health questions; this was mostly not visible to Brad rather than actually missing, and now explicitly covers readiness in the system prompt's scope description too.

Live-verified end-to-end against real local Ollama and 21 days of realistic seeded data (steps, HRV, sleep spanning real midnights): `/api/v1/health/metrics/sleep_analysis/history` correctly shows one combined total per night rather than two fragments; `/api/v1/health/readiness` and `/history` produce scores matching hand-computed expectations (100 on baseline days, 88 on a day with below-baseline HRV/sleep); the browser UI shows a working readiness card and 30-day graph, clean unit labels throughout ("44 ms", "58 bpm", "6200" steps with no unit), and asking the SirisAgent chat "How ready am I to train today?" correctly called `get_readiness_score` and reported the exact real numbers. The `TrainingConflictService` fix was confirmed by re-running `/api/v1/coach/conflict-check` before and after: it flipped from a false "insufficient_data" to the correct "reduced_recovery" against the same real seeded data.

## Consequences

- Backend: 283 tests pass (was 268 before this slice) -- 4 sleep-windowing tests, 1 evening-stability regression test, 7 `ReadinessService` tests, 1 `TrainingConflictService` timezone regression test, 2 SirisAgent tool tests.
- `HealthIngestService.to_local_date()` is now a small public seam other services can reuse for the same local-day comparison, rather than each service risking its own ad hoc (and potentially buggy) UTC-vs-local handling.
- The sleep cutoff (20:00) and the readiness score's exact formula (simple average of two baseline ratios, clamped) are both judgment calls made and documented here rather than negotiated in advance -- worth revisiting with real usage feedback, the same way Strength Score and Training Level's formulas were tuned after shipping rather than pre-specified.
- Discovered, live, that a global "Quick actions" FAB overlaps the Siris chat screen's own send button (unrelated pre-existing bug, flagged separately in ADR 094's session, not fixed here).
- `get_homelab_alerts` remains the most recently added SirisAgent tool before this slice; `get_readiness_score` brings the total to 13. Knowledge and Projects remain unscoped for the same structural reason noted in ADR 093/094.
